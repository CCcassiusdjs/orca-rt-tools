## Tick and release

The UCX-OS tick lasts 16 x (TIMER1CTC + 1) cycles (TIMER1 of `peripherals_minimal.vhd` counts from 0 to TIMER1CTC inclusive). `hal.c` writes TIMER1CTC = F_CPU / F_TIMER / 16 - 1, so the tick equals the release period T of A (`RELEASE_CYCLES` of `manycore_pe.sv`, T x F_CLK): 250 000 cycles at 500 MHz. The tick instants then keep a fixed phase to the releases, and the wait from each release to the dispatch of A is the same in every release; the boot time to the TIMER1 reset in `_hardware_init` and the path of the tick to the dispatch set its value. Run F (`logs/F.events.txt`) comes from a tree with TIMER1CTC = F_CPU / F_TIMER / 16 (tick of 250 016 cycles): `make tick-log` on it reports a dispatch spacing of 250 016 cycles and a wait that grows 16 cycles per release. Runs G (500 MHz) and H (434.912 MHz) come from tag r10-rc1 (TIMER1CTC = F_CPU / F_TIMER / 16 - 1): `make tick-log` passes on both, with a dispatch spacing of 250 000 and 217 456 cycles (the tick at the clock of the run), release_to_dispatch 1 303 cycles in each of the 34 releases, request_to_dispatch 1 690.5 cycles and an IRQ 4 acknowledgement latency of 387.5 cycles.

Release by tick (`lib/tick_release.c`, kernel and application built with `-DUCX_APP_IRQ4 -DUCX_APP_TICK -DUCX_TICK_RELEASE`): the release generator fires on every PE with a task (`app/<app>.sim`: `RELEASE_MASK`, `TICK_RELEASE=1`), the release interrupt counts the phases, and the tick hook of the kernel wakes the tasks whose phase has come. Each task of `weird_a.c` and of the applications of `rttools.ucxgen` waits for the tick of phase j + n(v) before it reads the input of iteration j, so it runs at most once per phase, as the phase model assumes. The stored runs A to H, CV, CV2 and MA come from the data-driven release (a task serves every iteration whose packets are in its queue): `weird_a_data` (Makefile of UCX-OS) and `rttools.ucxgen --release data` give that code, and the analyses of those logs take `--release data`. `python -m rttools.paper.phasecheck <metrics.json>` (`make phase-check` in `exp23`, `car-v-rtl` and `multiapp`) checks the executions per phase and the CPU per phase of a run against the model.

Interrupts: every interrupt handler of UCX-OS leaves interrupts disabled until the return of `_isr` (`arch/riscv/hf-riscv-e/crt0.s` returns through a5, which it does not save, so an interrupt inside the return of another one corrupts the return; `pkt-sim/tests/rtl/tb_cpu_irq.vhd`). `dispatch()` of the tick does not enable them, `yield()` restores the state of its caller and a task starts through `_task_start` (`hal.c`). `-DUCX_ISR_NESTING` builds the kernel of the stored runs A to H, CV, CV2, MA, W1 and CF, whose handlers enable interrupts before that return (`ISR_NESTING=1` in `simulate.sh` and `build_sw.sh`). `simulate.sh` writes `isr=no_nesting` or `isr=nesting` in `RUN_INFO`; the analyses copy it to `clock.isr` of `metrics.json`, `nesting` for a `RUN_INFO` without the line, and the references of the stored runs state `clock.isr = nesting`.

## Bound of the instrumentation writes (`metrics.json` `instrumentation`)

The kernel writes the instrumentation registers of `manycore_pe.sv` inside the measured times: `krnl_schedule` (`kernel/sched.c`) increments a 64-bit counter and calls `set_cacc`, `set_counter_1` and `set_counter_2` in each dispatch; `ucx_noc_send` and the receive interrupt (`lib/noc.c`) call `set_counter_3` and `set_counter_4` in each packet event. The RTL prints `scheduled`, `->` and `<-` at the writes of counters 2, 3 and 4. `rttools/paper/instrumentation.py` bounds their cycles from two listings of the image (`objdump --disassemble -Mno-aliases`, the `image.lst` of `build_sw.sh`): the build of `simulate.sh` and the same build with `-DUCX_NO_INSTRUMENTATION`.

| Step | Rule |
|---|---|
| Instructions of the writes | Per function that calls a write: instructions of the build with the writes outside the equal blocks of the alignment (difflib) of the mnemonic sequences of both builds, plus the instructions of each called write function (4: `lui`, `lw`, `sw`, `jalr`) |
| Checks | The unmatched instructions lie outside the loops of the function (strongly connected components of its control-flow graph); the write functions are straight-line code; every other function has the same mnemonic sequence in both builds |
| Cycles per instruction | `config.json` `instrumentation.cycles`, from `pkt-sim/tests/rtl/tb_cpu_cycles.vhd` (GHDL, HF-RISC core of `hw/cpu/core_rv32e` on the bus of `manycore_pe.sv`): ALU and `lui` 1, load and store 3 (also on the instrumentation registers: `stall_in = 0`, registers written at the clock edge of the address and read through `dly_address`, no wait state), jump 3, branch 3 taken and 1 not taken (the bound takes 3) |
| Charge to the events | A function whose write of a logged register lies on every path from the entry to a return (`krnl_schedule`: counter 2; `ucx_noc_send`: counter 3) charges its whole cost to each event of that register; otherwise (`irq3_handler`) each unmatched instruction must lie in a basic block with a logged write, and the block cost goes to that event |
| Bound per cluster | Per hyperperiod window: (dispatches x dispatch cost + sends x send cost + receives x receive cost) / iterations of the window, and its percent of the measured CPU time per iteration of the window; the maximum over the windows |

Run F (`logs/F.image.lst`, `logs/F.noinstr.lst`, `logs/F.software.txt`): riscv64-elf-gcc 12.2.0 and binutils 2.39 (Arch Linux packages); the image with the writes equals, byte for byte, the build of a `git archive` of tag exp23-F with the same packages. Runs G and H (`logs/G.image.lst`, `logs/G.noinstr.lst`, `logs/H.*`): the `image.lst` of the two builds of each run (`simulate.sh` and `software-without` at the `F_CLK` of the run, riscv64-elf-gcc 12.2.0 of `RUN_INFO`); against run F, only the functions of the tasks and `set_iter_mark` differ (iteration markers), and the bound per event stays 100 cycles per dispatch, 55 per send and 20 per receive.
